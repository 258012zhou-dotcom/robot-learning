# 向量环境与训练性能

## 快速复习

- `VectorEnv` 把多个独立环境包装成批量接口，Observation、Action 和 Reward 都多出环境批次维度。
- `SyncVectorEnv` 在一个进程中依次推进环境；接口向量化不等于计算并行。
- `AsyncVectorEnv` 使用多个 worker 进程并行推进环境，但需要支付进程启动、序列化、通信和同步开销。
- 公平比较不仅固定总 Transition 数，还要匹配每个环境的 seed、动作序列、轨迹长度与重置规则。
- 环境很轻时，异步可能更慢；单步计算足够重时，异步才可能产生加速。
- 采样吞吐量提高属于计算效率提升，不等于算法的样本效率提高。

## 从单环境到批量环境

普通环境的一次交互是：

```text
observation_t --policy--> action_t --environment.step--> observation_(t+1), reward
```

如果有 `B` 个环境，批量 Action 常见形状为 `(B, action_dim)`，批量 Observation 为 `(B, observation_dim)`。一次向量 `step()` 会产生 `B` 条 Transition：

```text
Transition 数 = vector step 数 × 环境数
```

比较 1 个环境与 4 个环境时，如果两边都调用 10000 次 `step()`，后者实际生成了 4 倍数据，并不公平。但仅固定总数也不够：一条 40000 步轨迹与四条 10000 步轨迹访问的状态可能不同。

修正后的实验 023 使用相同数量的独立环境。串行池、Sync、Async 都按相同的环境编号、seed 和动作推进，每个环境执行相同步数。`single` 仅保留为历史字段名，实际含义已是**普通环境的串行池**，不是一条更长的单环境轨迹。

## Sync 与 Async 的执行差别

### SyncVectorEnv

主进程依次调用每个环境，然后把结果堆叠为批次。它的价值主要是提供统一的批量接口、简化策略批量推理和数据组织。

近似开销可以理解为：

```text
一次 vector step 时间 ≈ B × 单环境 step 时间 + 批量整理开销
```

### AsyncVectorEnv

每个 worker 持有独立环境。主进程发出一批 Action，worker 并行计算，再把结果传回主进程：

```text
主进程 -> Action -> 多个 worker -> Observation/Reward -> 主进程
```

理想情况下，一次 vector step 接近最慢 worker 的计算时间；实际还要加上进程通信、序列化和等待成本：

```text
一次 vector step 时间 ≈ 最慢环境 step 时间 + 通信与同步开销
```

只有环境计算时间大到足以覆盖附加开销，Async 才值得使用。环境数量继续增加也不会无限加速，还会受到 CPU 核数、内存带宽和最慢 worker 的限制。

## 三个容易混淆的指标

### 吞吐量（throughput）

```text
throughput = 总 Transition 数 / rollout 时间
```

它表示单位时间获得多少训练数据，适合评价训练采样管线。

### 延迟（latency）

延迟关注一次请求多久返回。批量和并行可以提高总吞吐量，但单个样本的返回时间不一定更短。真实机器人在线控制通常更关心延迟和抖动，而不是离线训练的最大吞吐量。

### 样本效率（sample efficiency）

样本效率表示达到目标性能需要多少 Transition。并行环境通常只是更快地产生相同数量的数据，不会自动减少学习算法所需的数据量。

## 如何做公平、可解释的基准测试

1. 固定每种后端的总 Transition 数。
2. 在同一 workload 内保持环境参数、seed 和 Action 序列一致。
3. 正式计时前预热，减少首次调用和缓存初始化的影响。
4. 把环境构造时间与稳定 rollout 时间分开。
5. 重复运行并报告中位数和波动，不依赖单次偶然结果。
6. 使用逐元素比较或顺序敏感哈希，检查性能优化没有改变数值输出；求和校验不够。
7. 记录机器、worker 数量与环境负载；性能结论不能脱离运行条件推广。

计时结果本身受 CPU 调频、WSL 和后台任务影响，不要求逐次完全相同。固定 seed 保证的是实验数据可复现，而不是运行耗时可复现。

`[1,2]` 和 `[2,1]` 的 sum 都是 3，却不是同一条轨迹。当前 SHA-256 纳入形状及按时间、环境、分量排列的初始观测、动作、观测、奖励和结束标记；所有后端与重复都要匹配。它提供很强的数值一致性证据，但不检查 `info` 或隐藏物理状态，也不是数学上绝无碰撞的证明。

计时范围也要写清：当前 rollout 包含动作生成、step、检查及逐步哈希，初始化、预热和第二次 reset 单独记录。这是整个采样循环的吞吐，不是纯物理引擎速度。

## 多进程实现的工程边界

- worker 必须各自创建环境，不能共享同一个 MuJoCo `MjData`。
- 传给 worker 的环境工厂应可序列化；项目使用可调用的不可变 dataclass 保存构造参数。
- 启动多进程的脚本应使用 `if __name__ == "__main__":`，避免子进程重复执行整个脚本。
- 无论正常结束还是异常退出，都应调用 `close()` 回收 worker。
- 每个环境使用独立但可推导的 seed，例如 `base_seed + environment_index`。
- 自动重置可能改变终止帧语义。采集训练数据时要区分 `terminated`、`truncated` 以及重置后的 Observation。

## 与神经网络训练的关系

完整训练吞吐量还包括环境采样、数据搬运、策略推理、经验缓冲区和梯度更新。环境并行只是其中一段：

```text
环境采样 -> 批量 Observation -> GPU 策略推理 -> Action
        -> 经验存储 -> 批量训练更新
```

如果瓶颈在 GPU 训练，增加环境进程未必有效；如果 GPU 经常等待环境，增加并行环境可能提高利用率。正确方法是分别测量各阶段，而不是只看总训练时间猜测瓶颈。

## 当前项目证据

实验 023 的**旧协议**在 4 个向量环境、固定总 Transition 数和 3 次重复下记录：

- 轻负载：单环境约 26863 Transition/s，Sync 为 0.74 倍，Async 为 0.42 倍。
- 较重负载：单环境约 1466 Transition/s，Sync 为 0.99 倍，Async 为 2.50 倍。
- 旧程序只比较数值总和，未证明完整轨迹一致。

这些数字保留为历史记录，不能再作为严格公平的加速比证据：旧单环境是一条长轨迹，而向量环境是多条短轨迹。修正后的三后端哈希匹配已通过小规模测试，完整速度需要按新版协议重新测量，不能沿用旧的 2.50 倍。

实验未包含策略网络、GPU 训练和经验回放。即使新协议测得加速，也只证明该机器与负载下的采样效率，不证明策略更聪明或更省数据。
